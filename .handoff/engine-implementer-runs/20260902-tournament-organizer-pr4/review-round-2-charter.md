## 2. Phase 1 — The wire contract and its cross-language pins

**Units:** U1 + U2 + U3.

**Goal.** Make the broker the sole authority for tournament-action legality *on the wire*, make `CreateTournament.scoring` broker-defaultable, and give tournament bearer credentials an expiry, a constant-time comparison and a rotation RPC — all under one `LOBBY_PROTOCOL_VERSION` bump 5→6, propagated to every pin site in both languages. **Every reply that mints or re-mints a credential carries that credential's `expires_at_ms`** — the two mint replies as well as the renewal reply. No client behavior changes: the client keeps sending an explicit `scoring`, keeps ignoring the new server→client fields, and keeps its current credential storage.

**The mint replies must carry the expiry, and this is a Phase-1 obligation rather than a Phase-2 one.** The draft specifies (D2(c), and §3's Phase 2 goal below, and V12) that the client store holds *"an explicit expiry carried from the server's `expires_at_ms`"*, consulted by an `isValid` predicate on every read. Today the only reply that would carry one is `TournamentCredentialRenewed`; the two replies that actually mint a credential do not:

Left unfixed it forces the executor into exactly two bad outcomes: a client-side mirror of `TOURNAMENT_CREDENTIAL_TTL_MS` — which is the *same* duplicated-constant defect class this whole round exists to delete — or a renewal round-trip fired immediately after every create and join, which nothing in this charter plans, budgets or tests. **V12(b) is a design addition to U4, not merely a verification row — the charter must say so, because the draft does not specify it.** The draft's §4.6 describes `tournamentCredentialStore.ts` as *"`sessionStorage`, `TOURNAMENT_CREDENTIAL_STORAGE_KEY`, an expiry carried from the server, an `isValid` predicate consulted on every read, `load`/`save`/`clear`"*, every access `try/catch`-wrapped. **Read-path normalization and the retention cap appear nowhere in that list**, and neither is implied by `isValid`: `isValid` answers *"has this credential expired?"* — a per-entry temporal question — while the normalizer answers *"is this shaped like a credential at all?"* and the cap answers *"how many may be retained?"*. **The justification transfers, with one qualification the plan must record rather than paper over.** The **normalizer's** argument transfers verbatim: its own doc comment (`multiplayerStore.ts:1056-1060`) grounds it in *"persisted state is external input … a blob may be hand-edited, truncated, or written by a build whose shape or cap differed"*, and a `sessionStorage` blob is external input in precisely that sense — the draft's own §4.2 concedes as much when it records that `sessionStorage` *"removes durability but not readability — same-origin-script-readable exactly as `localStorage` is"*. What survives is a long-lived tab and a hand-written blob. **V27's partial-fill resolution — stated here rather than left to reading, because `scoring` is one all-or-nothing wire object.** It is a single `ScoringPolicy` struct with three *required* `u8` members, not three independently-optional fields, so "omit the policy" is simply not available field-by-field and a bare "an empty scoring field submits the omission" admits two incompatible readings. One is adopted:

**The rule: the frame omits `scoring` when and only when all three sub-fields are empty. A partial fill is not submitted at all — submit is disabled while some but not all of the three carry a value**, with the same affordance D5 already specifies for the below-floor case (*"submit is disabled until all three are filled"*). Three V27 rows pin it: **all three empty → `scoring` absent from the frame** (the auto path); **two filled, one empty → nothing is sent, the submit control is disabled** (not an omission, and not a frame carrying a manufactured `0`); positive control, **filling the third field re-enables submit and sends all three**.

**Why the other reading was rejected — "submit the policy whole, with each empty sibling as the `0` that `Number("")` yields, and let the broker refuse it."** Measured against the actual validator, it does not hold. `ScoringPolicy::new` (`crates/lobby-broker/src/tournament.rs:184-196`, read at source this session) rejects **only** `win_points == 0`; `draw_points` and `loss_points` of `0` are explicitly *valid*, and the function's own doc comment says why (`:180-183`: *"No ordering is imposed between the three values: organizer overrides are explicitly supported (some communities score draws as 0)"*). So that reading reaches a broker refusal only when the **win** field happens to be the empty one — V18's arm — and on every other partial fill it silently ships a `{n, 0, 0}` policy the organizer never typed and the broker happily accepts. That is exactly the *silently well-formed, so the authoritative validator never sees what the organizer typed* failure D6 exists to delete, reintroduced one field over. **Do not adopt it.**

**And the adopted rule is not the frontend re-deciding a broker rule.** The disable condition is *"how many of these three controls are filled"* — a property of the form, not of scoring. It makes no claim about which values are legal, imposes no bound, and would be identical if every numeric bound in `ScoringPolicy::new` changed tomorrow, so no client-side policy-validity predicate is introduced and the duplicated-policy class U5 deletes stays deleted. **V18 (Phase 1) remains the row that owns the broker's refusal of an actually-invalid policy**; Phase 2's plan should cite it so the boundary is legible, while noting that V27's partial-fill row deliberately never reaches it.

### 5.3 Merge constraint — no phase may be merged to `main` alone

Phase 1 lands server-side credential expiry (12h TTL, `TOURNAMENT_CREDENTIAL_TTL_MS`) **before** Phase 2 lands the client's renew-on-connect wiring. A tree that stops at Phase 1 compiles and passes its suites — the green-tree seam criterion is met — but would, if *deployed*, expire an organizer's authority after 12 hours with no client-side renewal path. **The deficit is sharper than "no renewal path", and V26 is what makes the sharper statement true rather than worse.** After Phase 1 the expiry is on the wire (V26) but no client code reads it: `adapter/types.ts` is untouched, so `expires_at_ms` is an unknown JSON field the TypeScript layer discards, and the credential store that would hold it does not exist until Phase 2. A Phase-1-only deployment therefore has a client that **cannot learn its own credential's expiry at all** — it discovers expiry only as an authorization failure on the next gated action, with no renewal wired to recover from it. That is strictly worse than a client that knows an expiry and lacks a renewal path, and it is the honest statement of why the two phases are a merge unit. The seam criterion for a charter is a green tree, not a shippable increment, and this charter satisfies it. The distinction is recorded here explicitly so no one mistakes phase 1 for a deployable checkpoint: **Phases 1 and 2 must reach `main` together, in the same PR.** Phase 3 may be split out afterwards if that is ever convenient.

## 7. Feasibility — is there a genuinely green-tree seam between each phase?

The draft *asserts* interim verification is structural (*"green tree built `--all-targets`, existing Rust and TypeScript suites passing with assertions unmoved"*). Verified rather than accepted, by reading how each wire field is actually added:

### 7.1 Seam after Phase 1 — **green, with named and bounded fallout**

**Server→client additions are safe by construction.** Phase 1 adds **four** required Rust fields in this direction, and they stand or fall on one argument: `ReportGate` on `PairingView`, `open_actions` and `scoring` on `TournamentSummary`, and **`expires_at_ms` on `TournamentCreated` and `TournamentJoined`** (§2's goal, pinned by V26).
